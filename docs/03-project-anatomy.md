# dbt Project Anatomy

This file explains what each directory and configuration file does.

You must know where things belong.

---

## Top-Level Structure

Typical project:

```
training_project/
├── analyses/
├── macros/
├── models/
├── seeds/
├── snapshots/
├── tests/
├── target/
├── dbt_project.yml
├── packages.yml
└── README.md
```

---

## models/

Most important directory.

Contains SQL models.

Each file:

* One SELECT statement
* One model

Example:

```
models/staging/stg_orders.sql
```

---

## macros/

Contains Jinja macros.

Reusable SQL logic.

You will use later.

---

## tests/

Schema tests and singular tests.

Usually defined via YAML.

---

## seeds/

CSV files.

Loaded as tables.

Example:

```
seeds/country_codes.csv
```

---

## snapshots/

Track slowly changing dimensions.

History tables.

---

## analyses/

Ad-hoc SQL.

Not materialized.

---

## target/

Generated by dbt.

Compiled SQL.

Never edit.

---

## dbt_project.yml

Main configuration file.

Defines:

* Project name
* Paths
* Model configs

---

## packages.yml

External packages.

Optional.

---

## Layered Modeling Approach

Common layers:

* **staging** - One model per source table, light cleanup, rename columns, cast types
* **intermediate** - Join staging models, apply business logic
* **marts** - Fact tables and dimension tables

---

## Naming Conventions

* `stg_` prefix for staging
* `int_` prefix for intermediate  
* `fct_` prefix for facts
* `dim_` prefix for dimensions

Use lowercase snake_case.

---

## YAML Configuration Files

Used for descriptions and tests.

Example:

```yaml
version: 2
models:
  - name: stg_orders
    description: Clean orders table
```

---

## Key Takeaway

90% of your work lives in `models/`.

Proper structure keeps projects predictable, reviewable, and scalable.
